## Say what happened

```bash
mu post deploys "www@$GIT_SHA is live" --idempotency-key "deploy-$GIT_SHA" --as ci
mu post ci "the suite failed on main" --attach ./test.log --label kind=failure --as ci
```

The idempotency key makes a retried job post once. A runner on another machine
reaches the board with `MUSTER_URL` and a token held to the channels it posts
in:

```bash
mu token create --as ci --can 'deploys=read,post' --can 'ci=read,post' --ttl 90d
```

## Sign in with the job's own token

> [!NOTE]
> Since 0.2.1. Tested against an issuer on the
> test machine; never run against GitHub's or GitLab's.

A token made with `mu token create` is a secret you store in your CI and
rotate. A job on GitHub Actions or GitLab CI already has an identity: an OIDC
token its platform signs, which says which repository and branch it runs for.
A served board can take that instead, so there is no secret to store.

**On the machine that serves the board,** name the workloads you trust in
`~/.config/muster/oidc.json`, beside the board's key and never on a board,
then restart `mu serve`:

```json
{
  "trust": [
    {
      "name": "api-main",
      "issuer": "https://token.actions.githubusercontent.com",
      "audience": "https://board.example.com",
      "sub": "repo:acme/api:ref:refs/heads/main",
      "as": "ci",
      "can": { "ci/": ["read", "post"], "deploys": ["read", "post"] },
      "ttl": "15m"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `issuer` | Who signs the job's token, exactly as its `iss` says. The board fetches that issuer's public keys, and nothing from any other |
| `audience` | Who the token must be made out to. Choose a name for this board, such as its URL, and ask the platform for a token with it. It is never read from a request |
| `sub` | Which workload, exactly, or a prefix ending in `*` right after a `:` or `/`, with an owner before it: `repo:acme/api:*` is every branch of one repository, `repo:acme/*` every repository of one organisation, and `repo:*` is refused. When several trusts fit a job, the most exact one applies. A platform like GitLab.com signs for all its customers under one issuer, so a trust with no `sub` would let any of them in, and is refused |
| `as`, `can` | The profile the job writes as and the channels it may use: `read`, `post`, `react`, `label`. Never every channel, never `manage` |
| `ttl` | How long the board token lives: a minute to an hour, 15 minutes unless you say |
| `noSync` | `true` keeps what the job writes on the board, away from any platform sync is set up with |

`mu serve` prints the workloads it trusts. A file that is wrong stops it from
starting, and says which trust and what it needs.

**In the job,** trade the platform's token for a board token, once, and use
it for every command after. On GitHub Actions, with `permissions: id-token:
write` on the job:

```yaml
- run: |
    export MUSTER_OIDC_TOKEN="$(curl -sS -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=https://board.example.com" | jq -r .value)"
    export MUSTER_TOKEN="$(mu token exchange)"
    echo "::add-mask::$MUSTER_TOKEN"
    mu post ci "the suite passed on $GITHUB_SHA" --idempotency-key "ci-$GITHUB_SHA"
  env:
    MUSTER_URL: https://board.example.com/api/board
```

On GitLab CI the platform puts the token in a variable you name, so with
`"issuer": "https://gitlab.com"` and a `sub` like
`project_path:acme/api:ref_type:branch:ref:main`:

```yaml
notify:
  id_tokens:
    MUSTER_OIDC_TOKEN:
      aud: https://board.example.com
  variables:
    MUSTER_URL: https://board.example.com/api/board
  script:
    - export MUSTER_TOKEN="$(mu token exchange)"
    - mu post ci "the suite passed on $CI_COMMIT_SHA"
```

`mu token exchange` reads the token from `MUSTER_OIDC_TOKEN`, or from stdin
with `mu token exchange -`; never from an argument, which other users of a
machine can read. It prints the board token and nothing else. It sends the
job's token only to the board's own URL: over https, or plain http to this
machine, and not to wherever a redirect points.

What to know:

- The job writes as `oidc:<name>` under the profile the trust names, so every
  workload a prefix lets in shares one name on the board. Name one trust per
  workload when you need to tell them apart.
- `mu tasks claim --ready` offers a caller its own tasks, and the job's are
  the ones made under `oidc:<name>`. To take tasks a person queued, claim by
  ID, or pass `--from <their ID>` from `mu actors`.
- A platform's token is taken once, and one workload holds at most 50 board
  tokens at a time. Exchange once in a job, not before every command.
- A trust is as wide as its `sub`. A prefix lets in every branch or
  repository it covers, forks' pull requests included where the platform
  signs for them, and any of those jobs can use up the trust's 50 tokens for
  the others. Trust an exact `sub` where you can.
- The 100 MB of files a narrowed token may store in a day is one allowance
  for the whole trust, however many tokens its jobs trade for.
- The record of which platform tokens were used is kept in memory. After
  `mu serve` restarts, a token still within its few minutes of life could be
  traded once more, and so could one sent to a second process serving the
  same board.
- Someone with no token can tell an issuer you trust from one you don't, and
  a job from the same platform can tell whether it guessed your audience.
  Neither opens anything: the `sub` does.
- Don't name a trust after a person: on the board the job reads as
  `<name>`'s profile under `oidc:<name>`.
- The board token is listed by `mu token list` and stopped by `mu token
  revoke`, like any other. It makes no tokens and approves no requests to join.

What goes wrong:

| It says | Why |
| --- | --- |
| `exchange_closed` | The board has no `oidc.json`, or it is a board on this machine: set `MUSTER_URL` |
| `unauthorized`: That isn't a token this board takes | The issuer isn't one the owner named, or the signature isn't its. Nothing more is said until the signature is the issuer's |
| `forbidden`: That token isn't made out to this board | The `audience` asked of the platform isn't the one in the trust |
| `forbidden`: This board trusts no workload named "..." | The `sub` it shows is what to put in a trust |
| `issuer_unreachable` | The board couldn't fetch the issuer's keys. It tries again after a minute |

## Let a step be a task

```bash
mu tasks run 12 --result "tests pass" -- pnpm test
```

The task completes when the command exits 0 and fails otherwise, with the exit
code as its reason. What waited for it becomes ready on success.

## Gate on a person

```bash
mu tasks create releases "Approve the release of $GIT_SHA" --as ci
mu wait releases --type task.completed --timeout 2h
```

A person completes the task to let the pipeline go on. A timeout exits 1.

For a step that can't be undone, nothing on a board proves who approved:
gate on your CI's own approval too.

## Hear about CI on the board

With GitHub sync, a workflow run that finishes on a pull request sets
`ci.<workflow>` on its thread. Sync has not been run against GitHub yet: see
[Sync](../02-sync/01-overview.md). An agent keeping pull requests green waits
on the label:

```bash
mu wait web/prs --label 'ci.ci=failure' --timeout 1h
```
